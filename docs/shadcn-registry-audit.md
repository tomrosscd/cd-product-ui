# shadcn registry compatibility audit — Step 1

Audit only. No exports have been renamed or rewritten. This establishes the classification, differences and proposed registry shape needed to scope the pilot (step 2). Nothing in `src/` changed as part of this document.

**Revision note:** the first pass of this audit contained real errors, caught by a direct code check rather than my read-through: it called `Progress` Radix-based and nearly compatible (it's fully native-element, custom, with a target marker and indeterminate state Radix's version doesn't have); it called `Table` compatible and claimed upstream has no dedicated caption slot (upstream's `TableCaption` exists — I hadn't fetched far enough into the file to see it); it called `Avatar` "probably compatible" without actually diffing it (it isn't — ours does initials-generation and image-fallback logic internally that upstream splits across three consumer-composed components); and its pilot recommendation silently reverted the tokens decision to "compiled CSS only" after we'd already agreed source + an adapted generator belongs in scope. It also mislabeled `ActionMenu`, `SegmentedControl` and `ToastRegion` as "migration candidates" despite each already having a distinct name from its nearest upstream concept (`DropdownMenu`, `ToggleGroup`, `sonner`) — by this document's own definition of that label (a name shared with upstream that makes a false compatibility promise), none of the three qualify. Corrected below. The corrected version also splits "close enough to investigate" from "proven compatible" — after the fixes, **nothing in this audit has actually been proven compatible yet**; that's the honest state step 4 exists to resolve, not something to claim in advance.

## Pinned upstream reference

"Pinned upstream equivalent" below means all of the following, not just a CLI version:

- **Source repository/revision:** `shadcn-ui/ui`, commit `3ba91b1cc83e1bbe4ab35a422ff2a694849c5048` (latest `main` at audit time, 9 September 2026), release tag `shadcn-ui@0.9.4`.
- **Style configuration:** `new-york-v4` — the only style shipped in the current Tailwind v4 registry (`apps/v4/registry/new-york-v4/ui/`). The old `default`/`new-york` split from the Tailwind v3 era no longer exists upstream.
- **Primitive family per item:** most components wrap Radix primitives via the **consolidated `radix-ui` npm package** (`^1.4.3`) — a single package re-exporting all primitives — not the individual `@radix-ui/react-*` packages this project pins (`@radix-ui/react-select@2.3.7`, `@radix-ui/react-popover@1.1.23`, etc.). This is a real dependency-shape difference on **every** Radix-based item, not just a version number. Some newer upstream components use a *different* primitive family entirely — noted per-row where that's the case (Combobox → Base UI, not Radix; Toast → the `sonner` package, not Radix Toast).
- **Supporting library versions in the upstream reference app** (`apps/v4/package.json`): `class-variance-authority@^0.7.1` (matches ours exactly), `@tanstack/react-table@^9.0.0` (ours: `8.21.3` — a major version behind), `react-day-picker@^9.7.0` (ours: `10.0.1` — we're ahead), `lucide-react@0.474.0` (we don't depend on it at all — see below), `cmdk@^1.1.1`, `sonner@^2.0.0`.
- **`cn()` helper:** upstream now imports `cn` from a standalone npm package literally named `cn` (re-exported from `apps/v4/lib/utils.ts`), which combines `clsx` + `tailwind-merge` logic. Ours is `clsx` only, no merge step — consistent with not authoring components in Tailwind utility strings (see main audit summary).
- **Icons:** every upstream component that needs an icon imports directly from `lucide-react` inline (`<ChevronDownIcon />`, `<Loader2Icon />`, etc.) — there is no icon-wrapper abstraction upstream. Ours routes every icon through a single `Icon` component with a closed set of named SVG paths and no `lucide-react` dependency at all. This is a structural choice on our side worth preserving (zero extra runtime dependency for icons), but it means no upstream component's icon usage copies over unchanged — every icon reference needs translating to our `<Icon name="..."/>` convention or the consumer needs to add `lucide-react` themselves for the vanilla fallback to render.

## How to read the table

- **Classification** — three labels, deliberately not two:
  - `Investigate for compatibility` — shares a name with upstream, and is structurally close enough (similar level of abstraction, comparable prop count) to be worth actually testing the fallback claim on in step 4. **Not a claim that it currently is compatible** — nothing in this audit has been proven compatible yet; this label just marks where testing is worth the effort.
  - `Migration candidate` — shares a name with an upstream component, and the composition model or prop contract differs enough that the fallback claim is very likely false without even needing step 4 to find out (compound-vs-flat mismatches, a name attached to the *wrong* upstream item, or real extra behaviour upstream doesn't attempt). Needs a rename or an explicit "no real fallback" note — a genuine decision, not a foregone one, and if the export is already public and released (check `etc/product-ui.api.md`), renaming it is a breaking change subject to this project's own backward-compatibility policy, not a free internal cleanup.
  - `Convert pattern` — either no upstream equivalent exists at all, or the name is already distinct from anything upstream ships (so there's no false-compatibility promise to correct in the first place). A different implementation underneath an already-distinct name is not, by itself, a reason to rename or rewrite.
- **Differences** covers props, composition (flat/data-driven vs. compound/children), behaviour, styling approach and dependencies — per your instruction, not just prop names.
- **Verification** is what step 4 needs to actually check per item — visual, keyboard, and (where relevant) form submission — not just a TypeScript build.

## Convert patterns — no upstream equivalent, no compatibility claim needed

## Font requirement — extended per your correction, and confirmed as a real, currently-live risk

The package source itself is clean (no `@font-face`, no binaries — this part of the original audit holds). But the Storybook *build* is a separate, real leak path, now directly confirmed rather than just flagged:

- `.storybook/preview-head.html` contains actual `@font-face` declarations pointing at `/local-fonts/Roobert-Regular.woff2`, `Roobert-Medium.woff2`, `Roobert-SemiBold.woff2`.
- `.storybook/main.ts` conditionally adds a `staticDirs` entry for `local-fonts` **only if the directory exists on the machine building it** (`existsSync('local-fonts') ? [...] : []`).
- On this machine, `local-fonts/` currently contains the real, licensed Roobert `.woff2` files, and — checked directly — **`storybook-static/` already has copies of them from a prior local build**, sitting right next to the git-tracked source.
- Both `local-fonts/` and `storybook-static/` are gitignored, so there's no exposure in the git repository itself. The risk is entirely in the *build step*: whoever (or whichever CI runner) executes `pnpm build-storybook` for a public deploy, if their machine happens to have `local-fonts/` present, will silently bundle the real licensed binaries into the exact output that would get pushed to GitHub Pages.

This needs a real fix before any public Storybook deployment, not just a manual check: an explicit "public build" mode (e.g. an env var Storybook's config checks) that force-excludes `local-fonts` regardless of local presence, used specifically by whatever job builds the publicly-deployed Storybook. A developer's own local `pnpm storybook`/`pnpm build-storybook` for personal preview can keep using local fonts as it does today; only the public-deploy path needs the guard.
